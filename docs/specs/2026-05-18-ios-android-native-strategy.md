# iOS·Android 네이티브 앱 전략 — 결정 문서

> 2026-05-18 · brainstorming 산출 · `docs/specs/2026-05-14-open-questions-resolutions.md` §4 를 **교체·구체화**

---

## 1. 결정 요약

> **품의 모바일 앱은 Phase 2에, 웹을 그대로 앱 껍데기에 담는 Capacitor wrap 으로 iOS·Android 동시 출시한다. 별도 codebase(React Native)는 만들지 않는다.**

- **방식**: Capacitor wrap (웹 = 앱, 한 codebase)
- **시점**: Phase 2 (핵심 M2·M3·M8·베타 이후). 착수는 트리거 신호로 판단
- **범위**: iOS + Android 동시 (Capacitor 한 살림으로 둘 다)
- **즉시 코드 변경**: 없음 (Phase 1은 future-proof 원칙만 유지)

---

## 2. 배경 · 동인

PO(김다원)가 iOS 네이티브 앱을 능동 고려(메모리 `project_ios_native_consideration`). 원하는 동인 4가지 전부: **앱스토어 노출·발견성 / 확실한 푸시 알림 / 신뢰감·정당성 / 네이티브 UX·존재감**.

동인 분해 — 무엇이 진짜 "네이티브"를 요구하나:

| 동인 | Capacitor wrap 으로 |
|---|---|
| 앱스토어 노출·발견성 | ✅ 100% (스토어 등록) |
| 신뢰감·정당성 | ✅ "정식 앱" |
| 확실한 푸시 알림 | ✅ 네이티브 푸시 플러그인 (iOS 웹푸시 16.4+ 불안정 우회) |
| 네이티브 UX·존재감 | 🟡 홈화면·전체화면 OK, 진짜 네이티브 제스처/성능은 한계 (초기엔 충분) |

→ 4개 중 3.5개를 Capacitor 하나로 충족. 품의 차별화 축은 *AI 동반자·정서·신뢰*지 네이티브 인터랙션 성능이 아니므로 RN 의 비싼 네이티브 UX 는 정당화가 약함.

---

## 3. 결정 (방식·시점·범위)

### 방식 — Capacitor wrap

기존 Next.js 웹을 Capacitor 로 감싸 네이티브 앱 셸 안에서 구동. 웹이 곧 앱(한 codebase). 알림은 Capacitor 네이티브 푸시 플러그인.

**RN 기각 사유**: 별도 codebase = 이중 관리·고비용, PO 학습곡선 큼(코드 직접 안 짬), web+앱 동기화 부담. IVF MVP·소규모 운영에 과투자.

### 시점 — Phase 2, 트리거 기반

핵심(M2 AI 동반자·M3 알림·M8 결제)과 베타(M9, 100~300 페어)가 끝난 뒤. **원칙: iOS/Android 작업이 핵심 일정을 밀지 않는다.**

### 범위 — iOS + Android 동시

Capacitor 는 같은 웹 코드로 두 플랫폼을 동시 산출. Google Play Console 개발자 등록은 **이미 완료**, Apple 개발자 등록은 어차피 진행 예정 → 등록 비용은 이 결정의 추가 비용이 아님(sunk/예정). Android 는 사실상 거의 공짜로 따라오고 심사도 Apple 보다 관대. 한 살림 → 두 스토어가 Capacitor 의 결정적 이점이며 현 상황과 정확히 맞물림.

## 4. 착수 트리거 (Phase 2 내 판단)

무작정 만들지 않고, 베타 데이터로 아래 신호 중 하나라도 뚜렷하면 착수:

| 신호 | 뜻 | 확인 방법 |
|---|---|---|
| **요청 신호** | 베타 사용자 다수가 "앱 없냐" / 스토어에서 못 찾음 | 베타 피드백·문의 집계 |
| **푸시 신호** | M3 알림에서 iOS 웹푸시 도달률 낮음 | M3 알림 도달률 측정 |
| **결제 신호** | 유료 전환(M8) 때 "정식 앱"이 신뢰·결제에 영향 | 결제 전환 인터뷰·데이터 |

→ 착수 시 **별도 spec → plan → 구현 cycle** (Capacitor 통합·푸시 플러그인·스토어 심사 대응). 본 문서는 그 진입 조건까지만 정의.

---

## 5. Phase 1 에서 지금 지킬 future-proof 조건

대부분 원칙·점검 항목 — **지금 새로 만들 코드 없음**.

| 조건 | 상태 |
|---|---|
| 링크·딥링크 = 웹 절대경로 URL only (앱 전용 스킴 금지) | ✅ 이미 적용 (페어 수락 `redirect_to`/초대 링크) — Universal Links/App Links 매핑 재사용 |
| 절대 URL 은 환경변수로 조립 (origin 하드코딩 금지) | ✅ 현 패턴 유지 (`NEXT_PUBLIC_SITE_URL` 등) |
| 알림은 웹푸시 ↔ 네이티브푸시 교체 가능한 인터페이스로 | 📌 M3 알림 **설계 시** 적용할 원칙 |
| 인증 세션이 앱 웹뷰(다른 origin)에서도 동작 | 📌 M2 인증 확장 시 점검 항목 (Supabase 쿠키 ↔ Capacitor 웹뷰) |
| 소셜 로그인 추가 시 in-app browser 호환 | 📌 해당 기능 생기면 (현재 이메일/비번이라 무관) |
| 모바일 웹뷰 기준 반응형·터치 타깃 | ✅ Tailwind 반응형 유지 |

✅ 이미/자동 3 · 📌 해당 작업 시 챙길 메모 3.

## 6. 비용 · 위험

**비용**: iOS 개발자 $99/년(어차피 지출 예정), Play Console $25(완료) — 추가 비용 아님. Phase 2 에 Capacitor·네이티브 푸시 연동·스토어 심사 대응(1회성 + 유지) 작업만. PO 부담 최소(웹 그대로).

**위험·완화**:

| 위험 | 완화 |
|---|---|
| 앱스토어 "단순 웹래퍼" 리젝 (Apple 4.2) | 네이티브 푸시·홈화면 통합 등 네이티브 기능 포함 → 통과 용이 |
| 웹뷰 성능 한계 | 품은 텍스트·폼·chat 위주라 영향 작음. 진짜 네이티브 필요가 명백해지면 그때 RN 재검토(트리거) |
| Capacitor 웹뷰 세션/쿠키 이슈 | Phase 2 착수 시 **로그인 흐름부터 검증** (조건 §5 인증 항목과 연결) |
